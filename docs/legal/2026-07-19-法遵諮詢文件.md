## 1. 一句話與類比

**一句話**：我們提供一套自動化軟體，讓使用者的加密貨幣交易帳戶「自動照著另一位公開交易者的動作做同樣的買賣」，使用者的資金全程留在自己名下的帳戶，我們只拿到一把「只能下單、不能提錢」的鑰匙。

**給不熟悉加密貨幣的類比**（三個，各有不精確之處，一併標註）：

| 類比 | 相似之處 | **不精確之處（重要）** |
|---|---|---|
| **證券戶的「下單權限委託」** | 客戶把下單權限給第三方，但錢還在客戶自己戶頭，第三方不能匯出 | 不精確：我們是**軟體自動執行**，沒有人在做判斷；且交易標的不是證券 |
| **自動跟隨的「訂單複製機」** | 我們只是把 A 的動作按比例複製到 B，不做任何自主判斷 | 不精確：我們**確實有一個例外會自主下單**——回撤保護的自動平倉（見第 4.3 節，這是誠實揭露的重點） |
| **記帳軟體連接銀行的「唯讀＋轉帳限制」授權** | 授權有明確的權限邊界，且邊界由平台強制而非由我們自律 | 不精確：我們的權限不是唯讀，我們**能下單**（會改變客戶的資產部位） |

## 2. 我們是什麼、不是什麼

### 2.1 我們**是**什麼

1. 一個**軟體服務**：客戶授權後，我們的程式持續監看一位「領頭交易者（下稱 **領頭者**）」在某個加密貨幣交易平台上的持倉變化，並在客戶自己的帳戶中按比例做出**相同方向**的交易。
2. 一個**技術中介**：我們是交易平台官方「推薦者分潤機制」的登記者，客戶的每一筆成交，平台會自動抽取一小筆費用直接付給我們（詳見第 3 節）。
3. 未來（規劃中，尚未實施）：一個**訂閱制軟體**，透過 Stripe（國際線上刷卡收款服務商）收取月費。

### 2.2 我們**不是**什麼（每一項都是事實陳述，可查證）

| 我們不做 | 事實依據 |
|---|---|
| **不保管客戶資金** | 客戶的錢從頭到尾在客戶自己名下的帳戶。我們沒有任何一個帳戶會收到客戶的交易本金。 |
| **不收受客戶資金** | 我們沒有代收轉付。客戶要入金，是自己從自己的交易所帳戶轉到自己的錢包，我們不經手。 |
| **不能提領客戶的錢** | 我們持有的鑰匙在**交易平台層級**就沒有提領與轉帳功能（見第 4.1 節，這是平台機制，不是我們的自律）。 |
| **不承諾任何報酬** | 沒有保本、沒有固定收益、沒有預期報酬率的宣稱。我們的文案有明文禁用詞清單（見第 5.3 節）。 |
| **不提供個別化投資建議** | 我們不分析客戶的財務狀況，不建議客戶買什麼，不對客戶說「現在該進場」。 |
| **不做交易決策**（一個例外） | 買什麼、何時買、買多少的判斷來自領頭者，不是我們。**例外**：回撤保護的自動平倉是我們的程式主動做的，見第 4.3 節。 |
| **不做法幣兌換** | 客戶如果要把新台幣換成加密貨幣，得自己去持牌交易所（例如 MAX、BitoPro）辦。這件事完全不在我們的系統內，也是我們刻意排除的範圍。 |
| **不代客戶保管密碼或私鑰** | 我們的介面明文寫「Filet 永遠不會請你輸入私鑰或助記詞」。技術上我們的系統也沒有接收私鑰的欄位。 |

## 3. 資金流圖解（文字版）

### 3.1 名詞先講清楚

- **錢包（wallet）**：客戶自己保管的一組加密金鑰，控制著鏈上的資產。像是「只有你有鑰匙的保險箱」。**鑰匙從頭到尾只在客戶的瀏覽器裡**，我們的伺服器沒有、也沒有接收它的程式碼路徑。
- **Hyperliquid**：一個去中心化的加密貨幣衍生性商品交易平台（境外，非台灣業者）。客戶在上面開的帳戶，控制權來自客戶的錢包鑰匙。
- **永續合約（perpetual / perp）**：一種沒有到期日的加密貨幣衍生性商品，可以做多也可以做空，可以開槓桿。經濟性質接近期貨。
- **agent key（代理金鑰，下稱「下單鑰匙」）**：交易平台原生提供的一種**受限授權**。持有者只能下單、改單、平倉，**在平台的規則層面就無法執行提領或轉帳**。

### 3.2 開通時發生什麼（一次性）

```
客戶用自己的瀏覽器錢包登入我們的網頁
        │
        ├─(1) 客戶簽署「授權下單鑰匙」（ApproveAgent）
        │      → 授權對象：我們產生的一把下單鑰匙
        │      → 這筆授權是客戶親自在自己錢包中簽的，記錄在區塊鏈上，公開可查
        │
        └─(2) 客戶簽署「同意推薦者費用上限」（ApproveBuilderFee）
               → 上限 0.1%，客戶親自簽署，區塊鏈上公開可查
               → 我們實際只收 0.02%（上限的五分之一）

同時：我們產生的那把下單鑰匙的私密部分，只存在我方伺服器一個
      獨立、不對外的服務中（檔案權限限制到單一系統帳號）。
      它從來不會回傳給網頁、不會出現在記錄檔中。
```

**關鍵事實**：整個開通過程中，**沒有任何一分錢從客戶轉到我們**。客戶簽的是兩份「授權」，不是付款。

### 3.3 運作時錢在哪裡

```
┌─────────────────────────────────────────────────────────┐
│  客戶自己名下的 Hyperliquid 帳戶                          │
│  （控制權來自客戶的錢包鑰匙，客戶隨時可自行提領）           │
│                                                          │
│   USDC 保證金  ←─── 客戶自己從自己的交易所帳戶轉入          │
│   持倉（多／空）  ←── 由我們的程式用「下單鑰匙」建立與調整   │
│                                                          │
│   我們能做的：下單、改單、平倉                             │
│   我們不能做的：提領、轉帳、改變帳戶所有權                  │
└─────────────────────────────────────────────────────────┘
        ↑
        │  我方伺服器上的程式（持有下單鑰匙）
        │  每 60 秒讀一次領頭者的持倉，若有變化則按比例
        │  在客戶帳戶中執行對應交易
        │
   ┌────┴──────────────────────────┐
   │ 領頭者（第三方交易者）的公開帳戶  │
   │ 我們只「讀」，完全不碰            │
   └───────────────────────────────┘
```

**客戶的資金從未離開客戶的帳戶。** 我們的程式改變的是這個帳戶裡的**持倉組成**（例如把 USDC 保證金拿去建立一個多單），而不是資產的歸屬。

### 3.4 每一筆費用怎麼產生

**費用一：推薦者費用（builder fee）——目前唯一的收入，也是唯一已實施的收費**

```
客戶的一筆成交（例如成交金額 100 USDC）
        │
        └─→ 交易平台在結算時，自動從這筆成交中抽 0.02%（= 0.02 USDC）
              直接記入我們指定的收款地址
              ↑
              這是交易平台的原生機制。我們沒有向客戶請款、
              沒有從客戶帳戶「拿」錢；是平台按客戶事先簽署的
              授權，在成交當下直接分配。
```

- **費率**：0.02%（萬分之二）。
- **上限**：客戶簽署的授權上限是 0.1%，我們實收 0.02%。要提高費率，**必須客戶重新簽署**——我們無法單方面調高超過已簽上限。
- **可查證性**：每一筆抽取都記錄在區塊鏈上，客戶可自行核對。我們已在測試網實測驗證費率確實是 0.02%（見第 5.2 節）。
- **收款形式**：我們收到的是 USDC（一種與美元 1:1 掛鉤的加密貨幣），入我們指定的鏈上地址。**我們沒有向客戶開立任何請款單，客戶也沒有向我們付款的動作。**

**費用二：訂閱月費（規劃中，尚未實施，預計 2026 年底）**

```
客戶 ──刷信用卡──→ Stripe（國際第三方金流商）──→ 我們的收款帳戶

Stripe 只處理這筆月費。Stripe 完全不接觸客戶的交易資金、
不接觸客戶的錢包、不接觸客戶在交易平台上的任何資產。
```

三種定價模型尚未拍板（純月費 / 免費層＋付費解鎖進階功能 / 依交易量分級），**這正是我們希望您的意見能協助決定的事項之一**（見問題 C3）。

## 4. 技術保證與其極限（誠實區分）

**我們認為這一節對責任認定最關鍵**：有些事情是「架構上不可能」，有些只是「我們承諾不做」。前者即使我們變壞、被駭、或倒閉都成立；後者只是政策，可以被改變。我們不希望在文件上把後者包裝成前者。

### 4.1 A 類：技術／平台層面**不可能**（不依賴我們的誠信）

| 保證 | 為什麼不可能 | 驗證狀況 |
|---|---|---|
| **我們無法提領或轉走客戶的錢** | 這是**交易平台自己的權限模型**：下單鑰匙這種授權類型，平台在受理指令時就不接受提領／轉帳類指令。不是我們選擇不做，是我們發不出這種指令。 | 已於測試網實測（2026-07-19）：全程僅使用下單鑰匙完成開倉、加倉、減倉、反手、平倉，主鑰匙零接觸。 |
| **我們的系統中不存在客戶的主鑰匙** | 開通流程設計成：客戶的簽名在客戶自己的瀏覽器完成，**簽好的授權由瀏覽器直接送往交易平台，不經過我們的伺服器**。我們的程式碼中沒有接收主鑰匙的路徑。 | 架構性設計，已有自動化測試釘住。 |
| **我們的軟體介面在結構上不含提領功能** | 我們的程式碼中，與交易所往來的介面**刻意不定義**提領與轉帳功能，並有自動化測試在每次修改時檢查這一點——若有人試圖加入，測試會失敗、無法通過。 | 已有結構性測試。 |
| **我們的網頁伺服器讀不到下單鑰匙** | 下單鑰匙由一個獨立、不對外的服務產生與保管，以作業系統層級的檔案權限隔離。網頁被入侵也拿不到下單能力。 | 已實作，部署驗收含權限測試。 |
| **客戶可隨時單方面撤銷授權** | 客戶可自行在交易平台上撤銷下單授權，**不需要我們同意、也不需要通知我們**。撤銷後我們的程式立刻失去下單能力。 | 平台原生機制。 |

### 4.2 B 類：**我們承諾**不做（依賴我們的誠信與內部控制，可被改變）

| 承諾 | 現行控制措施 | 誠實說明 |
|---|---|---|
| 我們只收 0.02%，不調到上限 0.1% | 程式常數，需改碼並重新部署 | **這是政策，不是技術限制。** 客戶簽的授權上限是 0.1%，我們理論上可以在不通知客戶的情況下調到 0.1%。我們認為這一點應該寫進契約成為契約義務（見問題 D2）。 |
| 我們只跟隨事先揭露的領頭者 | 程式設定檔，需人工修改並重啟 | 我們理論上可以把跟隨對象換成別人。目前測試階段是單一固定領頭者。 |
| 我們不會用客戶帳戶做未經揭露的交易 | 程式邏輯只做「鏡像領頭者」與「回撤保護平倉」兩種動作 | 我們持有下單鑰匙，**技術上能在客戶帳戶下任何交易指令**（包括開很大的槓桿）。這是本架構最大的殘餘風險，我們不打算淡化它。 |
| 我們不會任意停止服務而不通知 | 無自動化控制 | 純粹是承諾。 |

> **請特別注意 B 類的第三項**：非託管架構解決的是「我們拿不走錢」，**沒有解決「我們能用客戶的錢做出糟糕的交易」**。客戶的最大損失上限不是零，而是帳戶內的全部資金。我們認為這一點必須在風險揭露書中明白寫出，也是問題 E1 的核心。

### 4.3 C 類：安全機制及其**已知的失效情境**（我們不聲稱它一定有效）

我們設有「回撤保護」：當客戶帳戶淨值從高點下跌超過設定比例時，程式自動把所有持倉平掉並鎖死（需人工介入才能恢復）。

- 預設門檻：**短期 20%**（七日滾動窗）＋ **累計 40%**（自開始跟單以來的高水位）——任一觸發即啟動。

**但它有以下已知的失效與副作用情境，我們認為必須誠實揭露給客戶，也需要您評估責任影響**：

| 失效情境 | 說明 | 後果 |
|---|---|---|
| **極端行情可能平不掉** | 平倉是送出一張「最差可接受價格」的指令。若市場瞬間跳空超過我們設定的容忍幅度，指令可能無法成交。 | 保護未生效，虧損繼續擴大。**我們最需要它成功的時候，正是它最可能失敗的時候。** |
| **保護尚未生效的空窗期** | 保護需要累積一段時間的帳戶淨值樣本才能運作。剛開通、或伺服器重啟後的初期，保護處於「尚未生效」狀態。 | 此期間實質無保護。系統會發出警告，但**我們的設計選擇是「大聲告警但繼續跟單」，不是停止交易**——這是我們自己的取捨，可能需要重新檢討（見問題 E3）。 |
| **客戶自行轉出資金會被誤判為虧損** | 系統無法區分「客戶把錢轉走」與「交易虧損」，兩者都表現為淨值下降。 | 客戶轉出資金可能觸發**非必要的自動平倉**（客戶因此承受平倉成本與滑價）。目前以警語提醒客戶，正式修正排在下一階段。 |
| **不保證觸發時機最佳** | 20%／40% 是機械式門檻，不是判斷。 | 可能在最壞的價格平倉。 |

**我們的立場**：回撤保護是「盡力而為的風險緩解」，**不是任何形式的保證或保本**。但我們擔心：因為我們提供了這個機制，是否反而創造了某種注意義務或擔保責任？這是問題 E3。

## 5. 我們已經做到的合規性設計

列出這些不是為了自我辯護，而是讓您知道現有基礎，以便判斷還缺什麼。

### 5.1 架構層面

1. **非託管架構是刻意選擇的**：我們在 2026 年 6 月的規劃階段就明確否決了「託管資金池」方案（把客戶資金集中管理），理由正是台灣的吸金與虛擬資產監理風險。目前架構是那個決定的產物。
2. **權限最小化**：只取得下單權限，且該權限由交易平台強制，不依賴我們自律。
3. **授權由客戶親自簽署、鏈上可查**：每一份授權都有客戶自己的數位簽名，且公開可驗證。我們無法偽造，客戶也無法否認自己簽過（可查證性對雙方對等）。
4. **費率上限鏈上鎖定**：客戶簽的 0.1% 上限是平台強制的硬上限，我們無法逾越。
5. **實盤交易預設為關閉**：程式的預設狀態是不進行真實交易；開啟需要人工明確設定。
6. **啟用需人工核准**：客戶完成開通後不會自動開始交易，需要我們人工逐筆核對後以指令啟動。這是刻意的——避免自動化流程被攻擊者利用。

### A 類：業務定性與是否需要執照（**最高優先，會決定我們能不能做**）

#### A1. 在台灣，以自動化軟體、依客戶事先概括授權、於境外去中心化平台代客戶執行加密貨幣永續合約交易並按成交量收費，是否構成須經許可的金融業務？若構成，是哪一種（期貨顧問／期貨經理／全權委託投資／虛擬資產服務業／其他）？

- **為什麼問**：這是整個事業能否存在的前提。我們自己的初步理解是「加密貨幣永續合約可能不屬於證券投資信託及顧問法所稱的有價證券，也不一定屬於期貨交易法所稱的期貨」，但這是外行推測，需要您定位。
- **答案如何改變做法**：若構成須許可業務且我們無法取得許可 → **整個服務停止**，或改為「客戶自己下單、我們只提供訊號通知」的形態（大幅降低產品價值，但可能是唯一合法路徑）。若不構成 → 依 D 類問題完成契約文件後即可上線。

#### A2. 若加密貨幣永續合約在台灣法下**不被歸類為**有價證券或期貨，是否即意味著現行的投顧／代操相關法規完全不適用？還是仍可能透過其他規範（例如虛擬資產相關專法、洗錢防制法、金融消費者保護法）被納管？

- **為什麼問**：我們擔心出現「不在證券期貨法規內、但也不是完全自由」的灰色地帶，而我們誤以為灰色等於安全。
- **答案如何改變做法**：若存在其他納管路徑 → 我們需要提前準備該路徑的登記或遵循要求，而不是等到被要求才做。

#### A3. 台灣目前針對虛擬資產服務提供者（VASP）的規範，其涵蓋範圍是否包含「不保管客戶資產、僅提供自動交易執行的軟體服務」？我方是否需要辦理登記或申報？

- **為什麼問**：VASP 相關規範我們理解上主要針對「提供虛擬資產交換、移轉、保管、承銷」等業務，而我們自認都不做。但「代客執行交易」是否被解讀為某種形態的交換服務，我們不確定。
- **答案如何改變做法**：若需登記 → 我們需要評估單人事業體是否具備登記門檻（資本額、內控、法遵人員），若門檻過高則**商業模式不可行，需在投入更多開發前止損**。

#### A4. **【時效問題】** 就您所知，截至目前（2026 年 7 月），台灣關於虛擬資產服務的專法或子法的施行狀態為何？是否有已公布但尚未施行、將在我們預計上線時點（2026 年底至 2027 年初）生效的規範？

- **為什麼問**：我們的技術規劃排程橫跨至 2027 年第一季。若有法規在我們上線後生效，我們需要現在就把架構做成「屆時可調整」。
- **答案如何改變做法**：若有已知的未來法規 → 我們把相關的架構調整（例如身分驗證模組）預留接口，而不是屆時重寫。

#### A5. 我們規劃在後續階段**納入自有的交易策略作為「領頭者」之一**（亦即客戶跟隨的對象是我們自己操作的帳戶）。這是否使定性從「複製第三方公開交易的工具」轉變為「我方替客戶做投資決策」？

- **為什麼問**：**這是我們認為法律風險最高、但最容易被忽略的設計點。** 目前客戶跟隨的是不特定第三方交易者，我們主張自己只是傳導管道；但一旦領頭者是我們自己，我們就同時是決策者與執行者，「我們不做交易決策」的抗辯就消失了。
- **答案如何改變做法**：若這會改變定性 → 我們**放棄自有策略上架**（放棄一部分商業價值，但保住「純傳導」的定性），或將自有策略獨立為另一個需要不同法遵姿態的產品線。這是我們願意為法遵讓步的項目，但需要您明確告訴我們有沒有必要讓。

#### A6. 我們對領頭者的「篩選」行為（我們規劃依回撤歷史、策略風格、容量等準則挑選 3–5 位並上架），是否本身就構成投資建議或推薦？

- **為什麼問**：「我們提供一份精選名單」與「我們建議你跟這個人」的界線在哪裡，我們判斷不出來。若篩選即推薦，那即使領頭者是第三方，我們仍可能落入投顧範疇。
- **答案如何改變做法**：若構成推薦 → 我們改為「列出平台上所有公開交易者的客觀數據，由客戶自行選擇，我們不做任何排序或推薦」（產品體驗變差，但去除推薦性質）。若不構成 → 我們仍需確認揭露準則的方式（見 I2）。

### B 類：非託管架構是否足以避免「保管客戶資產」的認定

#### B1. 就本文件第 3 節與第 4.1 節所述的事實（客戶資金留在客戶自己名下帳戶、我方持有的授權在平台層級無提領權限、客戶可單方撤銷），是否足以認定我方**不構成**保管、持有或控制客戶資產？

- **為什麼問**：這是整個架構的立論基礎。若這個認定不成立，我們的所有設計取捨都要重來。
- **答案如何改變做法**：若不足以避免 → 我們需要知道**還差什麼**（例如：是否需要客戶資金與我方完全無任何技術關聯？是否需要第三方託管人？）。若第三方託管人是必要的，以單人事業體的規模，**這可能直接使商業模式不可行**。

#### B2. 我方持有「能改變客戶資產部位（將現金轉為槓桿持倉）但不能取走資產」的權限，在法律上是否構成某種形式的「控制」或「處分權」？

- **為什麼問**：這是我們自己最沒把握的地方。我們無法把客戶的錢拿走，但我們**能讓客戶的錢在幾秒內因為一個糟糕的持倉而大幅減損**。從結果看，這個權限造成損害的能力不亞於提領權。
- **答案如何改變做法**：若構成處分權 → 我們可能需要：(a) 在系統層面加入客戶可設定的**硬上限**（最大槓桿、最大單筆金額、可交易幣種白名單），把權限進一步縮小；(b) 相應調整契約中的責任條款。**這是純工程工作，我們願意做，只需要知道要不要做、做到什麼程度。**

#### B3. 我方在技術上「能夠」超出約定範圍下單（見第 4.2 節 B 類第三項）這件事本身，是否構成必須向客戶揭露的重大事項？未揭露是否可能構成隱匿？

- **為什麼問**：我們的傾向是主動揭露（我們認為誠實揭露比事後被質疑好），但擔心揭露反而被解讀為「明知風險仍為之」。
- **答案如何改變做法**：若應揭露 → 寫入風險揭露書，並可能配合 B2 的技術限縮。若揭露反而不利 → 我們需要您指導揭露的**措辭方式**。

#### B4. 我方持有的「下單鑰匙」若遭外部入侵竊取，攻擊者可以用它在客戶帳戶進行破壞性交易（但同樣無法提領）。此情境下我方的責任範圍為何？是否有必要投保或設定責任上限？

- **為什麼問**：我們已做了金鑰隔離（獨立服務、作業系統權限隔離、網頁層被打穿也拿不到），但不能宣稱絕對安全。
- **答案如何改變做法**：若責任重大 → 評估專業責任保險（單人事業體的可負擔性存疑），並在契約設定責任上限（若該上限在台灣法下有效，見 E4）。

### C 類：兩種收費模式的監管定性差異

#### C1. 「推薦者費用」（由交易平台依客戶事先簽署的授權，在每筆成交時自動抽取 0.02% 直接支付給我方）與「訂閱月費」（客戶主動刷卡支付固定金額），在監管定性上是否有差異？

- **為什麼問**：我們直覺認為「按交易量抽成」比「固定月費」更接近佣金或報酬分成，可能觸及更多規範；但也可能因為它是平台原生機制、我方未向客戶請款而定性不同。
- **答案如何改變做法**：若按量抽成定性較不利 → 我們可以**把主要收入改為訂閱月費，把推薦者費用降至極低甚至零**（推薦者費用目前是我們的主要收入設計，這個改變影響重大，但技術上只是改一個常數）。若兩者無差異 → 依商業考量自由選擇。

#### C2. 承上，「我方未向客戶請款、由平台在成交時自動分配」的事實，是否影響定性？（亦即：這是我方向客戶收費，還是平台向客戶收費後分潤給我方？）

- **為什麼問**：這關係到誰是收費主體、發票與稅務處理（見 J 類），也可能影響是否構成「收受報酬提供服務」。
- **答案如何改變做法**：影響開立憑證方式、營業稅處理、以及契約中費用條款的寫法。

#### C3. 訂閱月費的三種定價模型中，是否有任一種在定性上較為不利？
- **(A) 純月費**：單一價格，功能不限。
- **(B) 免費層＋付費解鎖**：免費用戶仍能跟單（我們仍賺推薦者費用），付費解鎖多領頭者與比例調整。
- **(C) 依交易量分級**：月費隨客戶 30 日交易量分檔。

- **為什麼問**：我們自己的擔憂是 **(C) 依交易量分級可能最接近按績效或按規模收費**，可能有不同的定性；而 **(B) 免費層可能構成招攬**。
- **答案如何改變做法**：**這題的答案會直接決定我們選哪一個定價模型**——這是尚未拍板的決策，我們正在等您的意見再定。

#### C4. 我們規劃的「推薦機制」有兩個選項：(a) 純邀請碼（推薦人與被推薦人皆無金錢利益）、(b) 返佣（推薦人可分得被推薦人產生費用的一部分）。返佣機制是否可能構成招攬或居間，而需要額外的資格或登記？

- **為什麼問**：返佣對成長幫助大，但我們直覺它的法遵複雜度高出一個量級。
- **答案如何改變做法**：若返佣有問題 → **只做邀請碼**（我們已傾向如此，但希望有專業意見背書後再定案）。

#### C5. 我方收取的推薦者費用是 USDC（美元穩定幣）而非法定貨幣，且直接進入鏈上地址。這是否產生額外的申報、兌換或外匯管制義務？

- **為什麼問**：我們最終需要把 USDC 換成新台幣以支付營運成本，這個環節我們完全不了解合規要求。
- **答案如何改變做法**：可能需要建立特定的兌換路徑（僅透過持牌交易所）與紀錄保存程序。

- **為什麼問**：客戶的兩筆授權簽名是密碼學上不可否認的，我們認為證據力很強，但不確定台灣法院的實務態度。
- **答案如何改變做法**：若不足 → 我們需要加入更正式的同意流程（例如完整條款頁面＋滾動至底部＋單獨勾選＋留存時間戳記）。這是純前端工作，可快速實施。

#### D4. 是否適用消費者保護法的定型化契約規範（審閱期間、應記載與不得記載事項）？若適用，具體要求為何？

- **為什麼問**：我們的客戶是自然人，服務是我們單方擬定的標準條款，直覺上可能適用。
- **答案如何改變做法**：若適用 → 需設計審閱期流程（例如條款頁與同意頁間隔），並檢視是否有主管機關公告的應記載事項。

#### D5. 風險揭露書應涵蓋哪些項目？我們初擬的清單是否有遺漏或不足？

我們初擬清單：(1) 可能損失全部本金；(2) 永續合約具槓桿，損失可能快於現貨；(3) 領頭者的過往績效不代表未來；(4) 領頭者可能隨時改變策略或停止交易；(5) 回撤保護不保證執行成功（含第 4.3 節四種失效情境）；(6) 我方技術上可能超出約定範圍下單；(7) 交易平台為境外業者，其倒閉、被駭、暫停服務的風險我方無法控制；(8) 智慧合約與區塊鏈本身的技術風險；(9) 加密貨幣價格波動極大；(10) 客戶自行轉出資金可能誤觸發保護性平倉。

- **為什麼問**：我們寧可揭露過度也不願不足，但需要專業判斷哪些是必要的、哪些的措辭需要調整。
- **答案如何改變做法**：直接決定風險揭露書內容，以及開通流程中必須強制客戶確認的項目數量與呈現方式。

#### D6. 交易平台（Hyperliquid）本身的服務條款是否可能限制我方以此方式提供服務？我方是否有義務確認客戶符合該平台的服務條件（例如地域限制）？

- **為什麼問**：我方是在該平台上以官方提供的機制運作，但我們沒有系統性檢視過該平台條款對「第三方代客交易服務」的規定，也不知道我們是否有義務為客戶把關。
- **答案如何改變做法**：若有義務 → 需要在開通流程加入地域與資格聲明（客戶自我聲明或實質查核，取決於義務程度）。

### E 類：責任邊界與損害賠償

#### E1. 客戶因跟單而虧損（純市場因素、系統正常運作）時，我方的責任邊界為何？「客戶已簽署風險揭露書」是否足以免責？

- **為什麼問**：這是最常發生的情境——客戶會虧錢，而且可能虧很多。
- **答案如何改變做法**：決定風險揭露書的措辭強度，以及是否需要設定客戶適格性條件（例如最低資產、投資經驗聲明、最高投入金額上限）。

#### E2. 客戶因**我方系統錯誤**（程式缺陷、伺服器中斷、跟單延遲、下錯單）而產生額外損失時，責任如何界定？契約中的責任上限條款（例如「以客戶已支付費用總額為限」）在台灣法下是否有效？

- **為什麼問**：軟體必然有缺陷。我們已有相當的測試覆蓋，但不可能保證無缺陷。
- **答案如何改變做法**：若責任上限有效 → 寫入契約。若無效或部分無效 → 我們需要重新評估風險承受能力，可能包括限制單一客戶的最大投入金額（技術上可實施）。

#### E3. **回撤保護「未能成功執行」時的責任**：我們提供了一個明示的保護機制並在文案中提及，但已知它在極端行情下可能失效（見第 4.3 節）。提供這個機制是否反而創造了我方的注意義務或擔保責任？

- **為什麼問**：**這是我們自己最擔心的責任問題。** 直覺上「有保護比沒保護好」，但法律上「宣稱有保護卻失效」可能比「從未宣稱有保護」更糟。
- **答案如何改變做法**：三種可能路徑，取決於您的意見：
  1. 若揭露充分即可免責 → 維持現狀，強化揭露措辭。
  2. 若創造了擔保責任 → 我們可能**在對外文案中完全不提及回撤保護**（保留機制但不作為賣點），僅在條款中以「盡力而為之風險緩解措施，不構成任何保證」描述。
  3. 若風險過高 → 極端情況下考慮移除自動平倉，改為「僅通知客戶、由客戶自行決定」（這會顯著降低產品的保護價值，是我們最不願意但願意考慮的選項）。

#### E4. 承 E3：目前「保護尚未生效期間仍繼續跟單」是我們的設計選擇（理由是首次部署即拒絕交易會使服務不可用）。從法律風險角度，是否應改為「保護未就緒則不交易」？

- **為什麼問**：這是一個工程取捨，我們選了可用性；但如果法律風險高，我們應該選安全性。
- **答案如何改變做法**：純程式修改，一天內可完成。**只需要您告訴我們該不該改。**

#### E5. 領頭者本身的行為（例如領頭者採取極端槓桿、或蓄意操作使跟單者受損）導致客戶虧損時，我方責任為何？我方是否有對領頭者進行盡職調查的義務？

- **為什麼問**：領頭者是我們不控制的第三方。我們規劃會做篩選（見 A6），但篩選程度與義務程度的關係不明。
- **答案如何改變做法**：若有盡職調查義務 → 我們需要建立正式的領頭者審查程序與紀錄（增加營運成本，但可行）。若無 → 我們在契約中明確聲明不對領頭者行為負責。**注意：這題的答案與 A6 可能互相牽制——做越多篩選越可能構成推薦，但做越少篩選可能違反盡職調查義務。若兩者衝突，我們需要您指出平衡點。**

#### E6. 若我方停止營運（單人事業體的實際風險），客戶的資金與持倉狀態為何？我方有無在停業前為客戶平倉或通知的義務？

- **為什麼問**：客戶資金不受影響（在客戶自己帳戶），但客戶可能持有我們建立的持倉而不自知，且失去自動管理。
- **答案如何改變做法**：可能需要建立「停業程序」條款（例如：提前 N 日通知、停止跟單但不強制平倉、指引客戶自行撤銷授權）。這也涉及我們是否應設立公司實體以區隔個人責任（見 J1）。

### F 類：洗錢防制與客戶盡職調查（**我們認為這是第二大風險，僅次於 A 類**）

#### F1. 我方目前**完全不進行任何身分驗證**——客戶只需要一個錢包地址即可使用，我們不知道客戶是誰、在哪裡、幾歲。這在現行法下是否可接受？

#### F2. 若需要身分驗證，驗證的程度為何（僅姓名與身分證明？含地址證明？資金來源？）？是否有交易金額門檻可豁免？

- **為什麼問**：程度差異會決定我們選擇哪一種驗證方案與成本。
- **答案如何改變做法**：直接決定技術選型與導入時程。

#### F3. 我方是否有義務對客戶的錢包地址進行制裁名單或可疑地址篩查？若客戶地址曾與非法活動關聯，我方的義務為何？

- **為什麼問**：市面上有商業服務可做鏈上地址風險評分，我們可以接上，但不知道是否必要。
- **答案如何改變做法**：若必要 → 導入地址篩查服務（技術上簡單，成本可控），並建立命中後的處理程序。

#### F4. 我方是否有可疑交易申報義務？若有，申報對象與程序為何？

- **為什麼問**：若有義務而我們不知道，這是刑事風險而非行政風險。
- **答案如何改變做法**：建立監控與申報程序，並可能需要指定法遵人員（單人事業體的可行性需評估）。

### H 類：個人資料保護

#### H1. 錢包地址（一串公開的區塊鏈識別碼）在台灣個人資料保護法下是否構成個人資料？

- **答案如何改變做法**：若構成 → 我們需要完整的隱私權政策、告知同意程序、當事人權利行使程序（查詢、更正、刪除）。若不構成 → 義務大幅簡化（但若 F1 要求身分驗證，這題就自動變成「構成」）。

#### H2. 我們會保存客戶的交易紀錄（跟單執行紀錄、成交明細、費用累計）。這些資料的蒐集目的、保存期限、與當事人權利應如何處理？特別是「刪除權」——區塊鏈上的紀錄我們**無法刪除**（技術上不可能），這如何處理？

- **為什麼問**：這是加密貨幣服務與個資法之間的結構性緊張：我們可以刪除自己資料庫裡的紀錄，但鏈上的紀錄是永久且公開的，任何人都可查，我們無權也無能力刪除。
- **答案如何改變做法**：需要在隱私權政策中明確說明此技術限制，並可能需要特殊的告知措辭。

#### H3. 訂閱功能上線後，Stripe 會蒐集客戶的姓名、電子郵件、付款資料，且資料儲存於境外。我方與 Stripe 的關係定性為何？我方是否需要辦理國際傳輸的相關程序？

- **為什麼問**：我們自己不儲存卡號，但客戶是為了使用我們的服務而向 Stripe 提供資料。
- **答案如何改變做法**：可能需要與 Stripe 簽署資料處理協議、在隱私權政策中揭露國際傳輸、並確認 Stripe 的合規文件是否足夠。

#### H4. 我方伺服器位於日本，客戶資料儲存於境外。是否需要辦理國際傳輸的申報或取得特別同意？

- **為什麼問**：伺服器選址是基於延遲考量（靠近交易平台），不是刻意規避。
- **答案如何改變做法**：若程序繁瑣 → 評估遷回台灣（會增加交易延遲，但技術上可行）。

### I 類：行銷用語紅線

#### I1. 我們現行的禁用詞清單是「固定收益、保證、存款、代操」。這個清單是否足夠？還有哪些用語應該禁止？

- **答案如何改變做法**：調整措辭，可能要求每次強調非託管時都必須並列虧損風險警語（我們的文案系統可以強制這個規則）。

#### I4. 我們在測試網實測驗證了若干技術保證（見第 5.2 節）。在行銷中引用「已實測驗證」是否有風險？（我們的擔憂是：測試網驗證不等於真實市場保證。）

- **為什麼問**：我們想誠實展示我們做了驗證，但不想造成過度信賴。
- **答案如何改變做法**：決定是否引用、以及必須並列的限制說明。

## 7. 我們自己最擔心的地方（不淡化）

依我們自評的嚴重程度排序。列出這些是希望您優先檢視。

1. **「非託管」解決了保管問題，但沒解決「代客決策與執行」問題。** 我們最強的抗辯是「錢在客戶手上」，但我們**確實在客戶帳戶中主動下單**。如果法律關注的是「誰在做交易決定」而不是「誰保管資產」，那我們的核心抗辯就打偏了。→ 問題 A1、B2。

2. **回撤保護是雙面刃。** 提供它是為了保護客戶，但它使我們從「純傳導管道」變成「有裁量的行為人」，並可能創造擔保責任。我們認真考慮過在對外文案中完全不提它。→ 問題 E3、E4。

3. **自有策略上架會摧毀「純傳導」的定性。** 我們的商業規劃中有這一項，但我們已經自己意識到它可能是整份文件裡最貴的一個設計決定。**我們願意放棄它。** → 問題 A5。

4. **完全沒有身分驗證。** 我們不知道客戶是誰。如果洗錢防制規範適用，這不是「還沒做好」，而是「根本沒做」。→ F 類全部。

5. **沒有任何正式契約文件。** 目前只有介面上的三個勾選框。若明天發生糾紛，我們沒有任何契約基礎。→ D 類全部。

6. **沒有地域限制。** 我們的網頁全球可及，我們也沒有阻擋任何地區。→ 問題 G2。

7. **主體未定。** 目前是個人。若有客戶求償，是對個人求償。→ 問題 J1。
