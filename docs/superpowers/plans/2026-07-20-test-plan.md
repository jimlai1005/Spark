## 0. 為什麼這份計畫不是功能清單

功能清單式的測試計畫會產生「每個功能都有測試」的錯覺，而本專案的事故**沒有一件**
是「某功能忘了寫測試」——全部是以下五類重複失效：

| # | 失效模式 | 已發生次數 | 症狀 |
|---|---|---|---|
| 1 | **混源比較**（同基準違規） | 3 | 數字看起來正常但錯 |
| 2 | **兩個進程各自推導同一條路徑** | 3 | 功能完全不通，或面板在引擎熔斷時報告一切正常 |
| 3 | **保護靜默失效** | 多次 | 下架無效、帳本遺失靜默回退、「查不到」當「沒問題」 |
| 4 | **文件會造成災難** | 4 | rsync 刪白名單、unit 硬編 mainnet、範本出貨實盤主網、exclude 不含機密 |
| 5 | **驗證本身失效** | 多次 | 測試全綠但變異存活、驗收指令誤報、**agent 虛構實跑證據** |

所以本計畫依**失效模式**組織，每一節回答的是「這類失效今天會不會再發生一次」。

## A. 誠實的覆蓋現況（以變異測試查證）

### A.1 方法

`cp` 備份 → 改壞一個不變量 → **跑全套測試** → 還原 → `sha256` 驗證還原無誤。
跑全套（而非猜測目標測試檔）才能回答真正的問題：**有沒有「任何一條」測試會咬**。

- 判定：**KILLED**＝有測試轉紅（不變量真的被保護）｜**SURVIVED**＝全綠（**裸露**）
- harness：`scratchpad/testplan_mut{,2,_web,_deploy}.py`（暫時性，未進 repo）

## B. 可執行的回歸測試腳本

### B.1 位置與用法

`scripts/filet_regression_check.py`——**一條指令跑完整站健康檢查**，
取代原本零散、不可重複、容易漏的手工 curl／ssh。

```bash
uv run python -m scripts.filet_regression_check              # 全部（35 條）
uv run python -m scripts.filet_regression_check --local      # 只跑本機測試＋lint
uv run python -m scripts.filet_regression_check --http       # 只跑站台唯讀檢查（20 條）
uv run python -m scripts.filet_regression_check --ssh        # 只跑伺服器結構性檢查（12 條）
uv run python -m scripts.filet_regression_check --fast       # 跳過單元測試，只 lint
```

環境變數可覆寫目標：`FILET_RC_HOST`／`FILET_RC_SSH`／`FILET_RC_SSH_KEY`／`FILET_RC_NODE_BIN`。

### B.2 涵蓋範圍（35 條）

**LOCAL（3）**：後端 pytest、前端 vitest、ruff lint。

**HTTP（20，全部唯讀）**：
- 九條前端路由（`/`、`/onboarding`、`/leaders`、`/capital`、`/performance`、
  `/pricing`、`/billing`、`/ops`、`/admin`）皆須 200
- TLS：憑證鏈有效、**非自簽**（`issuer != subject`）、到期日 > 14 天
- `/api/billing/plans` 契約：`billing_enabled` ＋ free/pro 方案 ＋ 每個 feature 的
  `text_key`/`included`/`shipped` 齊全
- **誠信檢查**：公開端點不得外洩 `price_id`／`customer_id`／`subscription_id`
- 六條需 session 的端點**必須回 401**——不接受「非 200 就算過」：
  **200＝閘門根本不在，500＝認證前就炸到資料層**，兩者都比 401 嚴重
- http → https 301 轉址

**SSH（12，本專案特有的結構性檢查）**：
- 三個常駐服務 active、**兩個 timer enabled**
- **`FILET_API_NETWORK=testnet`**（事故 2 的實機側防線）
- **交換目錄雙通道方向性**：三層 owner/group/mode，且第 2、3 層相對第 1 層**對調**
- ⭐ **引擎寫不進交換目錄根目錄**（單向性承重點；寫得進＝引擎可偽造客戶簽章記錄）
- api→engine 通道實際打通（api 寫得進 **且** engine 讀得到**同一個檔**，非同名兩個檔）
- engine→api 通道（心跳，方向相反）實際打通
- 白名單 `leaders.json` 為 `root:root 644`，且 ⭐ **filet-api 寫不到它**
- 四個 unit 皆顯式宣告 `FILET_LEADERS_PATH`（同源，非各自推導）
- 部署樹內無機密檔（排除 `.venv`——certifi 的 `cacert.pem` 是公開 CA bundle）

### B.3 刻意不涵蓋（與理由）

| 不涵蓋 | 理由 |
|---|---|
| 任何會動資金的請求 | 紅線。健康檢查絕不下單、不劃轉、不改配置 |
| 需錢包簽章的流程（登入／onboarding／選 leader／改配置） | 結構上無法自動化 → 移到 §C 手動案例 |
| Stripe checkout／webhook 端到端 | 需真實 test 金鑰；站台 `billing_enabled=false` |
| 引擎實際下單行為 | 需 activate 的 follower ＋ 注資錢包 → §D-2 |
| 讀取任何 `.env*` 內容 | 紅線 2。腳本只檢查**存在性**，永不讀內容 |
| 心跳**內容**正確性 | 目前零 follower，無心跳可讀 → 只驗到權限層（§D-3） |

### B.4 腳本自身的驗證（一個永遠通過的健康檢查等於沒有）

**① 首次實跑就抓到兩個真問題**（35 條中 2 條 FAIL）：
- `ruff lint` FAIL：腳本自己有個未使用的 `import re` → 已修
- `FILET_LEADERS_PATH` FAIL：**真實伺服器漂移**，見 §D-1

**② 刻意弄壞 → 確認會報錯**（兩次）：

```
# 把 FILET_API_NETWORK 的預期值改成 mainnet
  ✗ [ssh] FILET_API_NETWORK=testnet
      預期：mainnet（刻意弄壞的預期值）
      實際：testnet

# 在路由清單加入一條實際不存在的 /status
  ✗ [http] 路由 /status
      預期：HTTP 200
      實際：HTTP 404
```

**③ 還原後重跑通過**：`--http` → `總計 20 條：20 通過 / 0 失敗 / 0 略過｜結論：PASS`

**④ SKIP 不等於 PASS**：`FILET_RC_SSH_KEY=/nonexistent` 時 SSH 段標
`略過（**不等於通過**）` 並在摘要獨立計數，不會混進「通過」裡。

> ⚠️ 過程中的一個教訓：第一次的「弄壞路由」變異**靜默沒生效**（錨點跨行，
> `str.replace` 未命中），輸出看起來全綠。若當時就宣稱「已驗證會報錯」，那就是一次
> 虛構證據。**變異測試自己也需要「確認變異真的套用了」這一步**——harness 因此
> 對每個變異都斷言 `sha256` 有變化，`count(anchor) != 1` 一律 SKIP 而非靜默略過。

## C. 無法自動化的手動測試案例

以下四項結構上無法自動測（需要真實錢包簽章）。**每項都寫出「怎麼知道它壞了」**——
只寫「怎麼跑」的測試案例，執行者會把壞掉的狀態當成正常。

環境：`https://52-197-137-3.sslip.io`，**testnet**，需可簽章的錢包（MetaMask 等）。

### C.1 錢包登入（SIWE）

**步驟**
1. 開 `/`，點連接錢包，選帳號
2. 錢包跳出簽章請求 → 檢視訊息內容 → 簽署
3. 應導向 `/onboarding`

**預期**：訊息含 `52-197-137-3.sslip.io wants you to sign in with your Ethereum account:`、
你的位址、`URI: https://52-197-137-3.sslip.io`、一組 nonce。簽完進入 onboarding。

**怎麼知道它壞了**
- ⭐ **訊息裡的 domain／URI 不是 `52-197-137-3.sslip.io`** → 域分隔失效，這個簽章可能
  在別的站台被重放。**立刻拒簽並回報**
- 同一個 nonce 能簽第二次仍成功登入 → 單次使用失效（正常應該 401）
- 拒簽後顯示的錯誤訊息若是「你取消了簽署」以外的通用錯誤，或反過來把 401／網路錯
  都說成「你取消了簽署」→ 錯誤分流退化（A5 修復的回歸）
- 登入後重整頁面就被登出 → session cookie 沒設成 `secure`／`httponly` 或 TLS 有問題

### C.2 Onboarding 完整流程（含 approve agent／builder fee）

**步驟**
1. 登入後在 `/onboarding`，step 2 閱讀風險說明並確認
2. step 3（簽署）：頁面自動確保 agent 存在，然後出現兩張卡——**approve agent** 與
   **approve builder fee**，逐一點擊並簽章
3. step 4（入金）：依畫面指示存入 testnet USDC

**預期**：step 3 兩張卡都變成已完成；`/api/onboard/status` 反映 `agent_address` 存在、
builder fee 已授權。側欄步驟逐一打勾。

**怎麼知道它壞了**
- ⭐ **approve builder fee 的簽章內容裡的 builder 位址，不等於畫面上顯示的位址**
  → 信任錨斷裂，**拒簽**。同理 approve agent 的 agent 位址
- ⭐ **max builder fee 的數值大於畫面宣告的費率**（應為 f=20，即 0.02%）→ 拒簽
- 兩張卡都顯示完成，但 `/api/onboard/status` 仍說未授權 → 前端樂觀更新掩蓋了後端失敗
  （前端顯示與鏈上狀態不同源）
- 重整頁面後步驟倒退 → 步驟推導（`deriveStep`）依賴前端狀態而非鏈上查詢
- 簽章或組裝拋錯時**畫面毫無錯誤顯示**（已知：B4，fail-closed 不送 HL，非安全問題，
  但執行者會誤以為成功）

### C.3 選 leader（含簽章授權）

**步驟**
1. 開 `/leaders`，檢視策劃清單與各自的績效呈現
2. 選一個 leader，點選擇 → 錢包跳出簽章請求 → **先看訊息內容** → 簽署
3. 確認頁面顯示「下一個 cycle 生效」

**預期**：待簽訊息含**你剛剛點的那個 leader 位址**與一組 nonce。

**怎麼知道它壞了**
- ⭐⭐ **待簽訊息裡的 leader 位址不是你點的那一個** → 這正是 opus 找到的 C1 攻擊
  （被打穿的 API 讓你簽下對惡意 leader 的**真實**授權，引擎驗章會完美放行，
  稽核起來完全像是你自己要求的）。**立刻拒簽並回報**。
  前端本應在喚起錢包**之前**就擋下（W1 變異證實這道斷言有測試護著），
  所以若錢包真的跳出了不符的訊息，代表前端防線也失效了
- 績效區塊出現年化數字**卻沒有任何資料不足警示**，而該 leader 資料不足 90 天
  → §5.7a 的失效（程式碼對、部署對、**磁碟上的快照是舊碼產生的**）。
  查快照：`sudo systemctl start filet-leaderboard.service` 後重看
- 顯示的 MDD 小到不合理 → 15 分鐘取樣**系統性低估** MDD，這是已知極限不是 bug，
  但 UI 必須有標註；標註不見了就是回歸
- 頁面沒有「leader 報酬率是跟單者報酬率的**上界**不是期望值」這類揭露 → 誠信回歸

### C.4 調整資金配置（含簽章授權）

**步驟**
1. 開 `/capital`，調整投入本金與使用比例
2. 送出 → 錢包跳出簽章請求 → **先看訊息內容** → 簽署

**預期**：待簽訊息裡的 `allocated_capital` 與 `capital_utilization` **逐字等於**畫面數值；
提示明確說明「下一輪生效」，不是即時再平衡。

**怎麼知道它壞了**
- ⭐ **待簽訊息裡的數值與畫面不符** → 與 C.3 同型的信任錨攻擊，**拒簽**
  （W2 變異證實這道斷言有測試護著）
- 超界值（`capital_utilization` > 1 或 ≤ 0）被**默默夾取**成合法值而不是報錯
  → 政策邊界退化成 clamp。`capital_settings.py:257` 明寫「不夾取、不修正、不四捨五入，
  超界一律 raise」
- 畫面暗示「立即生效」或顯示了即時再平衡 → 語意回歸（會產生無謂 taker 成本）
- 送出後金額變了但引擎沒收到（`leader_changes.json`／`capital_settings.json` 沒更新）
  → 交換目錄通道斷了；用 `--ssh` 段的通道檢查交叉確認

## E. 建議的常態實踐

### E.1 哪些不變量**必須**有變異測試護著（判準，不是清單）

清單會過期，判準不會。**同時滿足以下兩條**的，必須有變異測試背書：

1. **它失效時是靜默的**——沒有例外、沒有紅字、沒有 500，系統看起來一切正常
2. **它的後果落在這三類之一**：碰錢（下單／配置／費用）、碰安全（授權／密鑰／
   白名單／單向性）、碰誠信呈現（給客戶看的數字、警示、揭露）

判準的操作方式：寫完一個保護後問「**如果我把這行刪掉，哪一條測試會紅？**」
答不出具體測試名稱，就當它不存在。答得出來，就實際刪一次確認——**本次 25 個變異裡，
20 個答得出來且確實紅了，5 個答不出來（全在部署產物層）**。

反過來說，**不需要**變異測試的：失效時會大聲爆炸的（型別錯、缺 import、
啟動時 fail-closed）、純樣式、純重構。

### E.2 部署後必跑

```bash
uv run python -m scripts.filet_regression_check          # 35 條，需 SSH 金鑰
```
無 SSH 金鑰的環境（如 CI）：`--local --http` 仍有 23 條有效檢查。
**SKIP 要當成「沒驗」看，不是「通過」。**

### E.3 改「資料生產者 → 投影 → API」欄位契約時的特殊檢查

RUNBOOK §5.7a 的教訓：`_leader_perf_public` 刻意用 `if k in row`（不是 `.get()`），
**後端刻意不給的鍵不得被憑空造出來**。代價是磁碟上的舊快照沒有新欄位，而**部署本身
不會重生快照**。實際發生過的失效：改版目的是「績效數字必須帶資料不足警示」，
部署後 API 照樣吐年化數字、**一個警示都沒有**——失效方向剛好是這次改版要根除的那一個。

**通則**：動這條鏈的欄位契約時，部署完必問一句
**「磁碟上的資料是舊碼產生的嗎？」** 然後手動重跑一次生產者並驗證新欄位真的在快照裡：

```bash
sudo systemctl start filet-leaderboard.service
# 再確認新欄位真的落地（改成你這次新增的欄位名）
```

本次實測目前快照**含**四個揭露欄位（`twr_insufficient_data`、
`max_drawdown_insufficient_data`、`annualized_return_insufficient_data`、
`annualized_return_extrapolated_from_days`），§5.7a 對現有欄位已滿足。

### E.4 兩條流程建議

1. **把 §A.3 的五條裸露不變量補成測試**——最高優先。機制已存在
   （`test_filet_leaders.py:214`），只是沒套滿。這五條各自對應一次真實事故。
2. **部署時寫入版本檔**（如 `/opt/filet/spark/DEPLOYED_COMMIT`）——目前伺服器不是
   git repo，無從得知站台跑的是哪個 commit（D-10），
   「站台全綠」因此**不構成本機 HEAD 可部署的證據**。

### E.5 關於 agent 回報（第 5 類失效）

本專案已有兩次 agent 虛構實跑證據的紀錄（其一為 opus 級，附了看起來很具體的表格）。
**判準：沒有主對話親跑的指令輸出，就不要說「完成」，不論有幾個 agent 說它完成了。**
本計畫的每個數字都附了產生它的指令；任何一條若無法用該指令復現，以復現結果為準。
